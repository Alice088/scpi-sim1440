## 3. Назначение разработки

### 3.1. Назначение системы

Система предназначена для эмуляции проверочной аппаратуры стенда испытаний. Система обеспечивает:

- работу произвольного числа виртуальных приборов по сетевому протоколу;
- имитацию отказов и помех канала связи;
- контроль модельного времени;
- регистрацию сеансов связи.

### 3.2. Область применения

Система используется для разработки и отладки ПО управления стендом без физического оборудования.

## 4. Термины и определения

| Термин | Определение |
|---|---|
| Прибор | эмулируемое устройство с командным интерфейсом, внутренним состоянием и моделью физических процессов |
| Слой помех | программная обёртка прибора, искажающая его отклик по заданным правилам |
| Сеанс | период активного TCP-соединения клиента с прибором |
| Стенд | совокупность запущенных приборов, объединённых внутренней сетью |

## 5. Требования к программе

### 5.1. Требования к функциональным характеристикам

Требования приведены с сохранением исходной нумерации. Пункты FR-01 и FR-03 в исходном черновике помечены как снятые; их содержание сохранено как базовая предпосылка системы и в объём приёмочного контроля не входит.

**FR-01. Модель прибора.** *(пункт снят в исходном черновике)*

Прибор реализуется через общий интерфейс. Интерфейс определяет: обработку текстовой команды с возвратом текстового ответа, внутреннее состояние, сброс состояния, шаг моделирования (tick). Конкретная реализация прибора (набор команд, физическая модель) определяется разработчиком реализации и не накладывает ограничений на остальную систему.

**FR-02. Транспорт.**

Система должна предоставлять прибор по TCP. Адрес и порт прибора должны задаваться конфигурацией. Протокол поверх TCP: текстовые строки в кодировке ASCII, разделитель команд — перевод строки, разделитель ответа — перевод строки. Одна строка входа — не более одной строки ответа.

**FR-03. Служебные команды.** *(пункт снят в исходном черновике)*

Каждый прибор обязан поддерживать команды: `*IDN?` (идентификатор прибора), `*RST` (сброс состояния в начальное, включая прекращение действующих режимов помех, если иное не задано конфигурацией).

**FR-04. Изоляция приборов.**

Каждый прибор должен исполняться в отдельном контейнере со своим IP-адресом во внутренней сети. Отказ одного прибора (падение процесса, обрыв соединений) не должен влиять на доступность остальных. Приборы не должны иметь каналов взаимодействия между собой.

**FR-05. Слой помех.**

Помехи должны реализовываться как обёртка над реализацией прибора и не требовать изменений в коде самого прибора. Слой помех должен поддерживать следующие типы искажений, включаемые независимо:

| Обозначение искажения | Искажение |
|---|---|
| `delay` | задержка ответа на заданную величину |
| `garbage` | замена ответа на мусорные данные |
| `break` | обрыв TCP-соединения |
| `truncate` | усечение ответа (передача префикса без завершения) |
| `silence` | игнорирование команды (отсутствие ответа) |

**FR-06. Управление помехами.**

Система должна задавать параметры помех конфигурацией на прибор: тип, вероятность срабатывания на команду, расписание (постоянно / на N-й команде / после времени T от старта). Слой помех должен поддерживать детерминированный режим: при фиксированном значении seed последовательность сбоев должна воспроизводиться одинаково при каждом запуске.

**FR-07. Модельное время.**

Прибор должен продвигать свою физическую модель дискретными шагами с заданной частотой. Система должна поддерживать коэффициент ускорения времени (например, 60×), задаваемый конфигурацией на прибор. Ускорение не должно изменять протокольную сторону (команды и ответы приходят в реальном времени).

**FR-08. Журналирование.**

Каждый прибор должен вести журнал сеанса: время события, направление (вход/выход), содержимое команды и ответа, факты срабатывания слоя помех. Журнал должен писаться в файл на том приборе. Формат — построчный, читаемый человеком.

**FR-09. Параллельные подключения.**

Прибор обязан корректно обрабатывать не менее двух одновременных TCP-подключений. Состояние прибора должно быть общим для всех подключений (подключения наблюдают одно устройство, а не копии).

**FR-10. Жизненный цикл.**

Подъём стенда целиком (все приборы) должен выполняться одной командой на основании файла конфигурации. Остановка — одной командой. Конфигурация должна описывать: число приборов, тип реализации каждого, адрес, параметры помех, коэффициент времени.

### 5.2. Требования к надёжности и нефункциональные требования

**NFR-01.** Язык реализации — Go. Код приборных реализаций не содержит сетевой логики, сетевой слой не содержит модельной логики.

**NFR-02.** Все внешние параметры (адреса, порты, режимы помех, seed, ускорение времени) задаются конфигурацией, в коде не зашиты.

**NFR-03.** Падение клиентского подключения (без корректного закрытия) не прерывает работу прибора.

Дополнительные требования к надёжности:

| № | Требование |
|---|---|
| Н-1 | Неизвестная команда не должна приводить к аварийному завершению прибора и не должна разрывать соединение. |
| Н-2 | Обрыв или некорректное закрытие соединения клиентом не должен влиять на обработку других подключений. |
| Н-3 | Повторный подъём уже поднятого стенда не должен приводить к ошибке. |
| Н-4 | Отсутствие контейнера или сети при остановке стенда не должно считаться ошибкой. |
| Н-5 | Состояние прибора должно быть защищено от одновременного доступа из разных подключений. |
| Н-6 | Система должна корректно завершаться по сигналам `SIGINT` и `SIGTERM`. |

## 9. Соответствие реализации версии 0.1 требованиям

| Требование | Состояние в версии 0.1 | Примечание |
|---|---|---|
| FR-01 | выполнено | контракт `core.Device`, реализация `BAT` |
| FR-02 | выполнено | адрес и порт задаются полем `addr` конфигурации |
| FR-03 | выполнено частично | `*IDN?` и `*RST` реализованы; `*RST` сбрасывает состояние прибора, но не прекращает действующие режимы помех |
| FR-04 | выполнено | каждый прибор запускается в отдельном контейнере со своим IP-адресом; каналы взаимодействия между приборами отсутствуют |
| FR-05 | выполнено | пять типов искажений реализованы как обёртка, код прибора не изменяется |
| FR-06 | выполнено частично | расписания `always`, `on_command`, `after_time` и вероятность реализованы как взаимоисключающие режимы одного искажения, а не как независимые параметры; детерминированный режим по `seed` реализован |
| FR-07 | выполнено частично | коэффициент ускорения задаётся полем `time_scale`; частота шага фиксирована (один шаг в секунду реального времени), отдельным параметром не задаётся |
| FR-08 | не реализовано | файловый журнал сеанса не ведётся; доступны журнал процесса (стандартный поток) и история сработавших воздействий в памяти |
| FR-09 | выполнено | каждое подключение обрабатывается отдельно, состояние прибора общее |
| FR-10 | выполнено | подъём и остановка стенда выполняются одной командой на основании конфигурации |
| NFR-01 | выполнено | приборные пакеты не содержат сетевой логики, транспортный пакет не содержит модельной логики |
| NFR-02 | выполнено частично | параметры приборов вынесены в конфигурацию; сетевые константы оркестратора зашиты в код |
| NFR-03 | выполнено | обрыв клиентского подключения не прерывает работу прибора |

Примечание к FR-02 и FR-05: искажение `garbage` подставляет в ответ символ `U+FFFD`, то есть не-ASCII символ, что выходит за рамки требования ASCII из FR-02. Мусорные данные задаются в коде слоя помех и конфигурацией не параметризованы, что расходится с NFR-02.

## 10. Порядок контроля и приёмки

| № | Критерий | Требование | Метод контроля |
|---|---|---|---|
| 1 | Модель прибора через общий интерфейс | FR-01 | обзор кода: интерфейс `core.Device` и его реализация |
| 2 | Транспорт и формат строк | FR-02 | `nc <ip> <port>`: команда и ответ разделяются переводом строки |

| 5 | Типы искажений | FR-05 | задание каждого искажения в конфигурации и наблюдение эффекта через `nc` |
| 6 | Управление помехами и seed | FR-06 | два запуска с одинаковым `seed` и одной последовательностью команд дают одинаковую картину сбоев |
| 7 | Модельное время | FR-07 | измерение изменения показаний прибора за известный интервал при заданном `time_scale` |
| 8 | Журнал сеанса | FR-08 | наличие файла журнала с построчными записями (не проверяется до реализации) |
| 9 | Параллельные подключения | FR-09 | два одновременных `nc`; команды в одном влияют на состояние, наблюдаемое в другом |
| 10 | Жизненный цикл | FR-10 | подъём и остановка стенда одной командой |
| 11 | Модульные тесты | Н-1 … Н-6 | `go test ./... -count=1` |
| 12 | Статический анализ и форматирование | — | `go vet ./...`, `gofmt -l ./cmd ./internal ./pkg` |
