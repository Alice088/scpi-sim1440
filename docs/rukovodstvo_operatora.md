## 1. Назначение программы

Руководство оператора определяет порядок работы с программой scpi-sim1440 — эмулятором стендовой аппаратуры, управляемой SCPI-командами через TCP.

Программа позволяет оператору:

- поднять виртуальный стенд с приборами в контейнерах Docker;
- подавать прибору команды и получать ответы;
- настраивать искажения канала связи и результатов измерений;
- воспроизводить сценарии помех детерминированно;
- останавливать и удалять стенд.

Описание архитектуры программы приведено в документе [opisanie.md](opisanie.md), требования — в [tz.md](tz.md) (FR-01 … FR-10, NFR-01 … NFR-03), учётные данные — в [pasport.md](pasport.md).

## 2. Условия выполнения программы

### 2.1. Требования к рабочему месту

| Компонент | Требование | Проверка |
|---|---|---|
| Операционная система | Linux | `uname -s` |
| Docker Engine | установлен, доступен текущему пользователю | `docker version` |
| Go | версия 1.27.1 или совместимая | `go version` |
| TCP-клиент | `nc` (netcat) | `nc -h` |
| Свободная подсеть | `172.30.0.0/24` не занята | `docker network ls` |

Для интерактивной оболочки в сети стенда (действие `work`) требуется образ `busybox`; он скачивается автоматически при первом запуске.

### 2.2. Подготовка к работе

1. Перейти в корень репозитория `scpi-sim1440`. Все команды оркестратора выполняются из корня репозитория: файл `config/devices.yaml` читается относительно текущего каталога, а образ собирается из текущего каталога.
2. Убедиться, что выполняется `docker version` без ошибок доступа.
3. Проверить конфигурацию `config/devices.yaml` (раздел 6).

### 2.3. Сборка образа прибора

Сборка выполняется автоматически при запуске стенда (действие `up`). Отдельная команда сборки:

```
docker build -t standemu .
```

Образ собирается в два этапа: сборка исполняемого файла `cmd/scpi-sim1440` в `golang:1.27-alpine`, затем упаковка в `gcr.io/distroless/static-debian12:nonroot`. Контейнер работает от непривилегированного пользователя `nonroot`.

## 3. Выполнение программы

### 3.1. Запуск стенда

```
go run ./cmd/manager -action up
```

Последовательность действий оркестратора: сборка образа `standemu`, создание сети `stand` (мост, `172.30.0.0/24`), создание и запуск контейнеров приборов, проверка IP-адресов, вывод сводки.

Пример вывода:

```
building image standemu
up: 1 devices
bat-1  172.30.0.11:5025
```

Проверка состояния стенда:

```
docker ps
docker network inspect stand
```

Ожидаемое состояние: сеть `stand` существует; контейнер `bat-1` работает с IP `172.30.0.11`.

### 3.2. Повторный запуск

Повторный запуск `-action up` при работающем стенде безопасен: работающие контейнеры пропускаются с сообщением `<name> already running, skip`, сеть не пересоздаётся. Остановленный вручную контейнер удаляется и создаётся заново.

### 3.3. Список устройств стенда

Приборы, их адреса и порт определяются конфигурацией `config/devices.yaml`. В поставке версии 0.1:

| Прибор | Тип | Адрес в сети стенда | Порт | Команды |
|---|---|---|---|---|
| `bat-1` | `bat` (АКБ) | `172.30.0.11` | 5025 | `*IDN?`, `*RST`, `MEAS:CHARGE?`, `MEAS:VOLT?`, `MEAS:CURR?` |

Адреса назначаются последовательно от `172.30.0.11`. При добавлении приборов в конфигурацию нумерация продолжается: второй прибор получит `172.30.0.12`, третий — `172.30.0.13`.

### 3.4. Интерактивная оболочка в сети стенда

```
go run ./cmd/manager -action work
```

Запускается контейнер `busybox` в сети `stand` с интерактивной оболочкой. Внутри оболочки доступна подсказка `nc <ip> <port>`, например:

```
nc 172.30.0.11 5025
```

### 3.5. Остановка стенда

```
go run ./cmd/manager -action down
```

Оркестратор останавливает контейнеры приборов и удаляет сеть `stand`. Отсутствие контейнера или сети не считается ошибкой. Контейнеры имеют флаг автоудаления, поэтому после остановки не остаются в списке.

### 3.6. Ручная проверка прибора через `nc`

Проверка выполняется с рабочего места или из оболочки `-action work`. Команда подаётся строкой, ответ читается строкой.

Сеанс 1. Идентификация прибора и измерение напряжения:

```
$ nc 172.30.0.11 5025
*IDN?
bat-1
MEAS:VOLT?
4.20
```

Сеанс 2. Измерение заряда и тока, сброс:

```
$ nc 172.30.0.11 5025
MEAS:CHARGE?
2.00
MEAS:CURR?
1.00
*RST
OK
MEAS:CHARGE?
2.00
```

Сеанс 3. Неизвестная команда — пустая строка, соединение сохраняется:

```
$ nc 172.30.0.11 5025
MEAS:TEMP?

MEAS:VOLT?
4.20
```

Сеанс 4. Наблюдение разряда. При поставке `time_scale: 60` и `draw: 1` модельное время идёт с ускорением 60:1, поэтому заряд уменьшается на 1 А·ч за один час модельного времени, то есть примерно за 60 с реального времени; полный разряд от 4,20 В до 3,00 В занимает около 120 с реального времени. Пример с выдержкой около 60 с между командами:

```
$ nc 172.30.0.11 5025
MEAS:CHARGE?
2.00
MEAS:VOLT?
4.20
(выдержка около 60 с)
MEAS:CHARGE?
1.00
MEAS:VOLT?
3.60
```

Ответы могут отличаться от приведённых из-за задержки 100 мс и установленных вероятностей искажений (раздел 6).

### 3.7. Сводная таблица команд прибора `bat` (версия 0.1; перечень расширяется)

| Команда | Назначение | Пример ответа |
|---|---|---|
| `*IDN?` | идентификация прибора | `bat-1` |
| `*RST` | сброс: полный заряд, состояние `idle`; режимы помех не прекращаются | `OK` |
| `MEAS:CHARGE?` | остаточный заряд, А·ч | `2.00` |
| `MEAS:VOLT?` | напряжение, В | `4.20` |
| `MEAS:CURR?` | ток разряда, А | `1.00` |
| любая иная | не поддерживается | пустая строка |

## 4. Сообщения оператору

### 4.1. Сообщения оркестратора

| Сообщение | Причина | Действия оператора |
|---|---|---|
| `building image standemu` | начата сборка образа | ожидать завершения |
| `up: N devices` | стенд поднят | проверить адреса в следующих строках |
| `down: N devices` | стенд остановлен | — |
| `<name> already running, skip` | контейнер уже работает | не требуется |
| `<name> exists but stopped, recreating` | контейнер остановлен | не требуется |
| `unknown action: <значение>` | недопустимое значение флага `-action` | указать `up`, `down` или `work` |
| `ip mismatch <name>: want <x>, got <y>` | контейнер получил не тот адрес | освободить адрес в подсети, повторить `down` и `up` |
| `unknown device: <тип>` | неизвестный тип прибора | исправить `type` в конфигурации |
| `out of range in devices; devices: N but you get M` | индекс прибора вне списка | исправить флаг `-devindex` |

### 4.2. Сообщения эмулятора прибора

| Сообщение | Причина | Действия оператора |
|---|---|---|
| `tcp up` | прибор начал принимать соединения | — |
| `failed listen <name> on <addr>: ...` | адрес занят или недоступен | освободить порт, проверить `addr` |
| `failed parse devices: ...` | конфигурация не найдена или содержит ошибку | запускать из корня репозитория, проверить YAML |
| `failed get device from factory: ...` | ошибка параметров прибора | проверить секцию `params` |
| `accept: ...` | ошибка приёма соединения | проверить состояние контейнера |
| `failed to write response: <значение>` | ошибка записи в соединение | соединение закрыто клиентом, вмешательство не требуется |
| `failed roll on <строка>` | сбой расчёта вероятности | обратиться к разработчику |

### 4.3. Типовые проблемы и их признаки

| Признак | Вероятная причина | Способ устранения |
|---|---|---|
| Контейнер не стартует или сразу завершается | ошибка конфигурации, занятый порт, ошибка запуска прибора | посмотреть журнал контейнера: `docker logs bat-1`; проверить `config/devices.yaml` |
| `docker logs` не содержит записей, контейнера нет в `docker ps -a` | контейнер имеет автоудаление и был удалён после завершения | запустить прибор вручную без автоудаления: `docker run --name bat-debug standemu -devindex 0`, затем `docker logs bat-debug` |
| `no route to host` при обращении к прибору | рабочий процесс вне сети `stand` либо блокировка трафика межсетевым экраном | запускать проверку из `-action work` или убедиться, что межсетевой экран пропускает трафик подсети `172.30.0.0/24` на порт 5025 |
| Соединение устанавливается, но ответ не приходит | сработало искажение `silence` | уменьшить вероятность или отключить `silence` в конфигурации |
| Соединение закрывается после ответа | сработало искажение `break` (в поставке — на 30-й команде) | изменить или отключить `break` в конфигурации |
| Ответ приходит обрезанным | сработало искажение `truncate` | изменить или отключить `truncate` в конфигурации |
| Вместо значения приходят символы `\ufffd#@%$` | сработало искажение `garbage` | изменить или отключить `garbage` в конфигурации |
| Ответ задерживается | включена задержка `delay` | уменьшить или отключить `delay` |
| Через 5 минут бездействия соединение закрывается | истёк таймаут неактивности | подать команду до истечения таймаута или переподключиться |
| `Cannot connect to the Docker daemon` | Docker не запущен или нет прав | запустить Docker, проверить членство пользователя в группе `docker` |
| `docker build: ...` | ошибка сборки образа | проверить доступность сети для загрузки базовых образов, повторить сборку |
| `parse devices: read config: open config/devices.yaml: no such file` | запуск не из корня репозитория | перейти в корень репозитория и повторить команду |

## 5. Действия оператора при аварийных ситуациях

| Ситуация | Действия |
|---|---|
| Стенд не отвечает | `docker ps`; при необходимости `-action down`, затем `-action up` |
| Контейнер прибора в состоянии перезапуска | `docker logs <name>`, устранить причину, выполнить `-action down` и `-action up` |
| Сеть `stand` осталась после сбоя | `-action down` удаляет сеть; при необходимости `docker network rm stand` |
| Требуется полностью сбросить состояние прибора | отправить команду `*RST` либо пересоздать контейнер через `-action down` и `-action up` |

## 6. Конфигурирование помех

### 6.1. Общие правила

Помехи описываются в секции `noise` прибора в файле `config/devices.yaml`. Каждое искажение имеет собственный режим срабатывания:

| Режим | Поле условия | Срабатывание |
|---|---|---|
| `always` | — | всегда |
| `on_command` | `n` | номер команды равен `n` |
| `after_time` | `t` | прошло больше `t` от старта прибора |
| `chance` | `chance` | детерминированный розыгрыш меньше `chance` |
| пустое значение | — | искажение отключено |

Длительности задаются в формате Go: `100ms`, `500ms`, `5s`, `1m`. Поле `seed` задаёт зерно розыгрыша: при одинаковых `seed`, конфигурации и последовательности команд срабатывания воспроизводятся. Номер команды ведётся суммарно по всем соединениям прибора, время отсчитывается от запуска процесса прибора. После изменения конфигурации необходимо пересоздать контейнеры: `-action down`, затем `-action up`.

### 6.2. Пример: задержка ответа на каждую команду

```yaml
    noise:
      delay:
        mode: always
        value: 250ms
```

Все ответы приходят с задержкой 250 мс.

### 6.3. Пример: разрыв соединения на заданной команде

```yaml
    noise:
      break:
        mode: on_command
        n: 10
```

Ответ на 10-ю команду прибора передаётся, после чего соединение закрывается.

### 6.4. Пример: искажение после истечения времени

```yaml
    noise:
      garbage:
        mode: after_time
        t: 30s
```

Через 30 с после запуска прибора каждое значение ответа заменяется на `\ufffd#@%$`.

### 6.5. Пример: вероятностные искажения с детерминированным зерном

```yaml
    noise:
      seed: 1440
      garbage:
        mode: chance
        chance: 0.10
      silence:
        mode: chance
        chance: 0.05
      truncate:
        mode: chance
        chance: 0.05
        cut_at: 5
```

Подмена значения выполняется в среднем в 10 % случаев, подавление ответа — в 5 %, усечение до 5 символов — в 5 %. При неизменном `seed` и той же последовательности команд картина искажений повторяется от запуска к запуску.

### 6.6. Пример: сочетание задержки и разрыва

```yaml
    noise:
      seed: 7
      delay:
        mode: always
        value: 100ms
      break:
        mode: on_command
        n: 30
```

Каждый ответ задерживается на 100 мс; на 30-й команде соединение закрывается после передачи ответа.

### 6.7. Полный пример конфигурации

```yaml
devices:
  - name: bat-1
    type: bat
    addr: ":5025"
    time_scale: 60
    noise:
      seed: 1440
      delay:
        mode: always
        value: 100ms
      garbage:
        mode: chance
        chance: 0.05
      silence:
        mode: chance
        chance: 0.05
      break:
        mode: on_command
        n: 30
      truncate:
        mode: chance
        chance: 0.05
        cut_at: 5
    params:
      capacity: 2
      empty_level: 3
      full_level: 4.2
      draw: 1
```

### 6.8. Отключение всех помех

Для чистой проверки прибора секцию `noise` следует оставить пустой:

```yaml
    noise: {}
```

## 7. Журналирование

Требование FR-08 технического задания [tz.md](tz.md) предусматривает запись журнала сеанса в файл на приборе. В версии 0.1 файловый журнал не ведётся. Оператору доступны:

| Источник | Содержание | Где смотреть |
|---|---|---|
| Журнал процесса прибора | запуск TCP-сервера (`tcp up`), ошибки приёма и записи ответа, сбои расчёта вероятности | вывод контейнера: `docker logs <имя прибора>` |
| История воздействий | факты срабатывания слоя помех с номером команды | в памяти процесса прибора, без внешнего доступа |

Рекомендуемая проверка журнала при подъёме стенда:

```
docker logs bat-1
```

Записи журнала сеанса (время, направление, команда, ответ, сработавшие воздействия) в версии 0.1 не сохраняются; при необходимости их фиксируют средствами клиента.
